## The Algorithm 8.0.0

> Doctrine only. What must hold is enforced by hooks and produced as artifacts, not performed as ceremony. v7.1.1 stays on disk for reference. Rationale and the list of what was cut: `PAI/DOCUMENTATION/Decisions/algorithm-v8-harness-first.md`.

### Doctrine

**Every piece of work moves CURRENT STATE to IDEAL STATE, and "done" is proven with tool evidence, not asserted.** Think, plan, and sequence however the task needs. The rules below are the parts that must hold regardless of which model is executing. **Write criteria only when "done" has a nameable probe.** If you can name the tool call that proves the work is finished, write criteria. If you can't, notes are the record and that is enough. Most day-to-day work needs no criteria file.

**Where criteria live:**
- **Project notes directory (preferred when one exists):** a lightweight criteria file with only `## Goal`, `## Criteria`, and `## Decisions`, kept beside the notes the work already lives in.
- **Project with persistent identity:** `<project>/ISA.md`, full format per `PAI/DOCUMENTATION/IsaFormat.md`.
- **One-shot multi-session task:** `MEMORY/WORK/{slug}/ISA.md`.

Don't invent parallel artifacts (acceptance.yaml, separate test specs). The criteria are the tests.

**ID-stability:** ISC IDs never re-number on edit. Splits become `ISC-N.M`; drops become tombstones (`- [ ] ISC-N: [DROPPED — see Decisions]`). Reconcile depends on this.

### ISC Quality

> **Split until each criterion is one binary tool probe.** A criterion is granular enough when a single tool call (`Read`, `Grep`, `Bash`, `curl`, screenshot, `SELECT`, `bun test`, etc.) returns yes/no on whether it's met. If you cannot name the probe, the criterion is not yet atomic — split it. If the criterion needs human judgment, name the tool-verifiable proxy that stands in for the judgment.

| Test | Split when... |
|------|--------------|
| "And"/"With" | Joins two verifiable things |
| Independent failure | Part A can pass while B fails |
| Scope words | "all", "every", "complete" → enumerate |
| Domain boundary | Crosses UI/API/data/logic → one per boundary |
| **No nameable probe** | You can't say which tool would verify it |

At least one `Anti:` criterion (what must NOT happen). Markers: `- [ ]` pending, `- [x]` passed with evidence, `- [DEFERRED-VERIFY]` probe impossible now, requires a follow-up task ID.

### Scope

For project work or an ambiguous ask, record four answers as one `## Decisions` entry before building: (1) what changes in the world, (2) how could this be wrong to build, (3) what is explicitly excluded, (4) what evidence will show it worked. No visible gate block. On resume, the resume hook asks whether the reason is still true and whether there is now a better approach.

### Reproduce-First

**For a reported bug, capture a reproduction before reading the suspect code path.**

| Symptom | Required reproduction |
|---------|----------------------|
| Web/UI bug | `Skill("Interceptor")` screenshot or network trace |
| HTTP endpoint failure | `curl -i` showing the broken response |
| CLI tool failure | Actual stdout/stderr captured |
| Deploy/build failure | The actual error message from the log |
| Test failure | The failing test output with assertion |
| Data inconsistency | `SELECT` result showing the wrong row/value |
| Agent/hook misbehavior | Synthetic input via `bun run` showing the broken behavior |

If reproduction is unsafe or impossible, skip it and log why in `## Decisions`. After reproducing, fix at the point of ingestion, not where the symptom surfaces.

### Verification

**No ISC criterion may transition `[ ]` → `[x]` without verification evidence captured in the same tool call block that claims it, or the immediately-following block.**

| ISC type | Minimum verification tool call |
|----------|-------------------------------|
| File write | `Read` the file and confirm expected content |
| Code edit | `Grep` for the new symbol/line, or `Read` the specific range |
| Command execution | `Bash` with the actual command and checked output |
| HTTP/API change | `curl -i` with status + body shape check |
| Deploy | Live URL `curl` or `Interceptor` screenshot showing deployed version |
| UI change | `Skill("Interceptor")` screenshot at the target route |
| Schema/DB change | `SELECT` confirming the migration landed |
| Config/env change | Read-back of the file confirming the new value is on disk |

Evidence goes in `## Verification` as `ISC-N: [probe type] — [one-line evidence, quoted command output or file content]`. The verify-lint hook blocks `phase: complete` when an `[x]` has no evidence line with a quoted action or result, e.g. `` `grep -c x f.ts` → `2` ``.

**Forbidden language**: "should work", "should be", "expected to", "the change is in place" (without Read/Grep), "done" (without tool evidence), "no errors" (without the actual log).

**Rule 1 — Live-probe user-facing artifacts.**

| Artifact type | Required probe |
|---------------|----------------|
| Web page / UI | Browser screenshot via `Skill("Interceptor")` |
| HTTP endpoint | `curl` response with expected status + body shape |
| CLI tool output | Actual stdout captured |
| Database write | Subsequent `SELECT` confirming the write |
| File write | `Read` confirming content matches intent |
| Hook / skill | Direct `bun run` invocation with synthetic input |
| Deploy | Verify deployed version string, not just successful push |

**High-stakes** means either: the ISA's `effort:` is `deep` or `comprehensive`, or the work changes `CLAUDE.md`, `PAI/ALGORITHM/`, `hooks/`, `settings.json`, or content leaving `~/.claude`. **Rule 2 — Advisor at commitment boundaries** on high-stakes multi-step work: before committing to an approach, when two attempts fail, and before declaring a durable deliverable done. `bun ~/.claude/PAI/TOOLS/Inference.ts --mode advisor --auto-state "TASK: ..." "QUESTION: ..."`

**Rule 2a — Cross-vendor audit (Cato) on high-stakes work, via direct Bash only, never via `Agent()`.** An agent wrapper lets a model narrate the audit instead of running it (incidents 2026-06-15, 2026-07-10).

```bash
bun ~/.claude/PAI/TOOLS/CrossVendorAudit.ts --slug "${SLUG}" --advisor-verdict "${ADVISOR_VERDICT}"
```

| Cato verdict | Action |
|--------------|--------|
| `pass` with no `critical` findings | Proceed |
| `concerns` | Surface findings to user, ask approve / iterate / defer |
| `fail` OR any `critical` finding | Block `phase: complete`, enter Rule 3 |
| `skipped` | Log to `cato-findings.jsonl`, proceed (narrow infra-skip allowance) |

**Rule 3 — Surface conflicts.** If results contradict the advisor or Cato, re-call with the conflict stated. Maximum TWO re-calls on the same conflict, then escalate to the user.

**Re-read before done.** Re-read the user's last message and check every explicit ask against what shipped. A miss means not done.

### Learning Router

Default disposition: SKIP. Keep only what a future session with zero context would need.

| Type | Target | Gate |
|------|--------|------|
| knowledge | `MEMORY/KNOWLEDGE/{People\|Companies\|Ideas\|Research}/` | inline |
| rule / gotcha | `CLAUDE.md` rules, or the skill's Gotchas | inline |
| state | project notes, or `USER/PROJECTS/PROJECTS.md` | inline |
| identity, doctrine, hook, permission | the respective file | **surface to user first** |

### Context Recovery

Read the ISA or the project notes directory and continue. Do not narrate the recovery. `MEMORY/STATE/work.json` has the session registry.

### Routing and Harness

The prompt hook emits the executing model and a reason, never a mode or a routing decision (routing: `DOCUMENTATION/Routing/ModelRouting.md`). Cheaper executing models get extra injected scaffolds from `PAI/ALGORITHM/model-scaffolds.yaml`. Phase state, checkpoint commits, and reflection telemetry are written by hooks, not by the model. Preflight gates, premortem, deliverable manifests, delegation and parallelism gates, and ephemeral feature files are on demand in `PAI/ALGORITHM/on-demand.md`.
